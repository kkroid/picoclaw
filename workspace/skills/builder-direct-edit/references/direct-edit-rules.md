# 直接改码规则

目标：约束 Builder 优先做真实文件修改，而不是输出阅读性元信息。

## 开始前必须读取的内容

- `pubspec.yaml`
- `lib/` 下现有入口与页面文件
- `test/` 下现有测试文件
- 模板工程里已经存在的资源和目录

如果没有先查看这些文件，就不要开始改。

## 输出约束

以下内容不能作为主要结果：

- `Tasks`
- `Commands`
- `Uses`
- 历史 finish 标记
- `_apply.sh` 说明
- Markdown 补丁文本
- “下面是将要修改的文件”之类草稿
- 整段完整文件草稿但实际未写入工作区

允许存在非常短的说明，但前提是本轮已经完成真实文件修改。

## 改动优先级

1. 先移除默认 counter demo 残留。
2. 再补核心页面骨架：首页概览、记一笔、账单列表。
3. 再补数据实体、仓储和本地持久化接线。
4. 最后补测试和收口修改。

## 最小可接受实现

对记账类 Flutter App，至少要看到这些迹象：

- `lib/main.dart` 不再是默认 counter demo。
- 已有首页概览页面。
- 已有新增账单表单或等价录入流程。
- 已有账单列表展示。
- 数据能通过本地持久化层读写，而不是只存在临时内存变量。

## 明确禁止

- 只输出规划，不改代码。
- 只改 `test/widget_test.dart` 来掩盖功能缺失。
- 只加 TODO 注释、占位文案或空页面。
- 用新的大架构替换模板既有结构。
- 引入额外代码生成链路，例如 `build_runner`、`*.g.dart`、`freezed`，除非上层明确允许。

## 结束前自查

- 这轮是否真的修改了工作区文件。
- 是否仍保留默认 Flutter counter demo。
- 是否已经补出至少一个真实用户流程，而不是只有页面壳子。
- 是否把结果留在现有工程结构中，而不是散落成说明文本。
